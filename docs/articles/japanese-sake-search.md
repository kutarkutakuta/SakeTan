AIに頼むと、検索欄も、候補の一覧も、追加ボタンも作ってくれます。コードが揃うのは早いです。

でも、その検索欄に何を入れて、どの候補が先頭に出て、そのあと何のキーを押すのか。そこは自分で考えたいところです。

日本酒の銘柄から酒屋を探せる「さけたん」というWebアプリを作っています。今回は、酒屋の取扱銘柄を登録する画面で入れた、小さな工夫の話です。Next.jsとReact、Supabaseを使っていますが、仕組み自体はかなり素朴です。

## 「一ノ蔵」で探したら、一ノ蔵を先頭に出したい

この画面では、すでに登録されている銘柄を検索して、その酒屋の「取扱あり」に追加します。一つの店に何銘柄も登録するので、検索して追加、また検索して追加、という操作を繰り返します。

検索対象には、銘柄名とその読み、それから酒蔵名と酒蔵の読みを含めています。蔵の名前は覚えているけど銘柄名は出てこない、という探し方もできるようにしたかったからです。

ここで、銘柄名と酒蔵名が同じ場合に少し困ります。たとえば、テストにも使っているこの組み合わせ。

| 銘柄 | 酒蔵 |
| --- | --- |
| 一ノ蔵 | 一ノ蔵 |
| Again | 一ノ蔵 |

「いちのくら」で検索すると、両方ともヒットします。検索としては合っています。でも、銘柄名をそのまま入力したときには、その銘柄が先頭にいてほしい。

そこで、取扱銘柄の編集画面では、次の順に並べています。名前と読みは同じ扱いです。

| 優先順位 | 一致の種類 |
| --- | --- |
| 1 | 銘柄の完全一致 |
| 2 | 酒蔵の完全一致 |
| 3 | 銘柄の前方一致 |
| 4 | 酒蔵の前方一致 |
| 5 | 銘柄の部分一致 |
| 6 | 酒蔵の部分一致 |

同じ種類の一致なら、「検索文字列の長さ ÷ 対象文字列の長さ」が大きいものを優先します。前方一致どうしなら、検索した言葉に対して余分な文字が少ないほうを上に出す、ということです。それでも決まらなければ、画面で選んだ銘柄順・蔵元順・県順で並べます。

蔵名まで検索できる範囲は残しつつ、名前を指定して探したときには目的の銘柄へたどり着きやすくしました。なお、この順位は取扱銘柄の編集画面のものです。一覧の人気ランキング順などとは分けています。

## 先頭に出せるなら、Enterで追加したい

目的の銘柄が先頭に出るなら、そのままEnterで追加できると楽です。入力して、マウスに持ち替えて、追加ボタンを押して、また検索欄に戻る。この往復を減らしたかった。

そこで「Enterで先頭を追加」を入れました。検索欄にフォーカスがある状態でEnterを押すと、表示されている先頭の銘柄を、その店の取扱銘柄に追加します。銘柄マスターを新規作成する操作ではありません。

ここまで考えると、検索順位も登録補助の一部になります。先頭に何を出すかで、Enterを押した結果が変わるからです。

もちろん、候補があればいつでも追加していいわけではありません。実装では、次の条件で対象を決めています。

```ts
const firstAddableBrand =
  !catalogBusy &&
  isBrowsingCatalog &&
  visibleBrands.length > 0 &&
  !relationStatuses.has(visibleBrands[0].id) &&
  !working.has(visibleBrands[0].id)
    ? visibleBrands[0]
    : null;
```

読み込みが終わっていること。検索文字列や都道府県・かなの絞り込みがあること。そして、先頭の銘柄にその店との取扱関係がなく、追加処理中でもないこと。

画面には、追加できるときだけ「Enterで先頭を追加」と表示し、対象の行には左側に目印を付けています。キーボードを押す前に、どの銘柄が追加されるかを見て判断できるようにしました。

## 先頭が追加済みなら、そこで止まる

細かいところですが、先頭が追加済みだったときは、Enterによる追加を無効にしています。

「追加できる最初の候補」を探せば、2件目や3件目を登録することもできます。でも、先頭を見てEnterを押したのに別の銘柄が追加されるのは避けたい。対象はあくまで、表示されている先頭です。

追加が成功すると、その銘柄に取扱関係ができます。同じ検索結果のままもう一度Enterを押しても、次の銘柄が続けて登録されることはありません。

何件も登録するための補助ですが、連打して次々に入れる動きにはしていません。次の銘柄を登録するときは、検索語を入れ直すなどして、また先頭を確認してもらいます。

## 日本語入力のEnterもある

Enterで追加するなら、日本語の変換確定とぶつからないようにする必要があります。

かなを入力して漢字に変換し、確定のためにEnterを押す。その操作で銘柄まで追加されてしまうと困ります。キーイベントでは、変換中とキーの押しっぱなしを除外しています。

```tsx
onKeyDown={(event) => {
  if (
    event.key !== "Enter" ||
    event.repeat ||
    event.nativeEvent.isComposing ||
    event.nativeEvent.keyCode === 229 ||
    !firstAddableBrand
  )
    return;

  event.preventDefault();
  void addBrand(firstAddableBrand);
}}
```

`isComposing` が変換中の判定、`repeat` がキーの繰り返しの判定です。[UI Events仕様](https://www.w3.org/TR/uievents/)に定義があります。`preventDefault()` は、追加する条件が揃ったときだけ呼んでいます。

`keyCode === 229` は、IME入力に対する互換性対応として残しています。`keyCode` はレガシーなAPIなので、この補助判定に限定しています。IMEまわりはブラウザーとの組み合わせでも挙動が変わるため、この条件だけであらゆる環境をカバーできると考えず、対象環境での操作確認が必要です。[レガシーキー属性の仕様](https://www.w3.org/TR/uievents/#legacy-key-attributes)も参照しています。

さらに、追加関数の中でも、処理中の銘柄IDを `useRef` の `Set` に入れています。再描画を待っている間に同じ処理が始まるのを防ぐためです。DBにも、店舗と銘柄の組み合わせに一意制約を置いています。

## 「ず」と「づ」、「じ」と「ぢ」でも探せるようにする

もう一つ、検索入力で吸収することにしたのが濁音・連濁で揺れやすい仮名の違いです。

たとえば、読みが「つづきのさけ」なら「つずき」でも、読みが「ちぢみのさけ」なら「ちじみ」でも見つかるようにしています。これは説明用の架空の銘柄ですが、テストでもこの組み合わせを使っています。

登録されている読みはそのまま残して、比較するときだけ「づ」を「ず」、「ぢ」を「じ」に揃えます。

```ts
export function normalizeKanaSearchText(value: string) {
  return value.replace(/づ/gu, "ず").replace(/ぢ/gu, "じ");
}
```

この処理を検索入力と検索対象の両方にかけます。ブラウザー内の絞り込みだけでなく、Supabaseの検索RPC側にも「づ→ず」「ぢ→じ」の変換を入れています。

今のところ、ひらがなの「づ／ず」「ぢ／じ」が対象です。表記を揃えたからといって同じ銘柄と決めるわけではなく、候補には元の銘柄名と酒蔵名を出しています。

この一致判定と、銘柄の一致を酒蔵の一致より上に出す並び順は、自動テストにも残しました。IMEで変換してEnterを押すところは、文字列や順位のテストとは別に、画面で確認する部分です。

## 次の操作まで決めてから、AIに頼む

検索欄を作って、ヒットしたものを並べる。そこからもう少し考えると、「名前が一致した銘柄を先頭にしたい」「それならEnterで追加したい」「追加済みならそこで止めたい」と、決めることが出てきます。

どれも、大きな機能ではありません。でも、何件も登録する画面では、こういう小さなところが毎回の操作に効いてきます。

タイトルには「AIでも考えてくれない」と書きましたが、こうした条件を伝えれば、実装は手伝ってくれます。候補を出してもらうこともできます。ただ、どの動きにするかを選ぶには、このアプリで何を繰り返すのかを考える必要がありました。

検索結果の先頭を見て、そのままEnterを押せる。さけたんでは、その一連の操作を作りたかった、という話です。
